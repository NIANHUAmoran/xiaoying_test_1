# 复盘与下一步

最难的部分是让“建议已经保存”和“用户已经确认”保持独立，同时让重复提交重新检查当前排期。实现中把原始要求、候选时段和确认位分开存储，并用同一草稿行更新建议；当前占用变化后可改建议而不悄悄改用户硬性要求。

第一次完整测试暴露了 SQLite 插入占位符数量与表字段数量不一致，导致所有实际保存失败。修正后重新执行测试；随后补充并发竞争、查询后占用变化、确认事件、配置加载与真实接入回归测试，最终 31 项通过。这说明必须验证真实落盘结果，不能只看模型或上层函数声称“已保存”。

另一项发现是外部排期快照必须能释放旧占用，不能只不断追加；因此显式传入排期时会事务替换外部快照，而已有草稿保留预留。待确认草稿也预留候选，防止多个素材得到同一候选位置。

已学到的工程原则是：先跑通最小纵向链路；让模型决定动作、工具限制权限；规则与保存事实由可测试的代码核验；测试同时看输出状态与数据库副作用；写清验证来源，避免把离线演示说成真实模型效果。

真实接入进一步暴露了语义问题：模型把保存待确认建议视为擅自修改硬性要求，因此选择提前停止。程序没有伪造成功，留下了未完成记录。明确“建议不等于授权变更”后，真实模型改为选择 19:00 并保存待确认草稿；正常与信息缺失路径也验证通过。这个问题只有连接真实模型后才被发现，离线策略不能替代它。

用时记录见 [delivery-status.json](../examples/delivery-status.json)。原始约 15 分钟记录是首次源文件创建至离线交付的自动采集窗口，不含前一轮读题规划、后续配置等待与真实模型接入，也不代表候选人的人工用时。真实模型完成时间另列于该文件和验证汇总。候选人提交时应补录自己的实际总投入。

下一步由候选人亲自复核已归档的三条真实路径，根据实际业务需要补充草稿撤销与授权撤回、时段过期、多渠道和区间冲突。真实模型业务样例已通过；远程交付还需填写 GitHub 仓库地址、评审权限和最终 commit SHA，目前未完成远程提交。
